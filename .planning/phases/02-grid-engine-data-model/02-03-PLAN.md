**lib.rs** — Add a new WASM endpoint following the established JSON-in/JSON-out pattern:

```rust
#[wasm_bindgen]
pub fn generate_grid(config_json: &str) -> String {
    // 1. Deserialize PuzzleConfig from JSON
    // 2. Call PuzzleGrid::new(config)
    // 3. Build a serializable response containing:
    //    - grid summary: rows, cols, width_mm, height_mm
    //    - piece_breakdown: { total, corners, edges, interior }
    //    - edge_summary: { h_edge_count, v_edge_count, border_count, internal_count }
    //    - seed_used: the actual seed string (for display/sharing)
    // 4. Serialize to JSON and return
    // On error: return {"error": "message"}
}
```

Create a `GridResponse` struct (with Serialize) that wraps the grid data for JSON output. This is a WASM-layer concern — it selects what data to expose, not the full internal Edge structs. Include:
- `rows: u32`, `cols: u32`, `width_mm: f64`, `height_mm: f64`
- `seed: String`
- `piece_breakdown: PieceBreakdown` (reuse from puzzle-core)
- `h_edge_count: usize`, `v_edge_count: usize`
- `pieces: Vec<PieceInfo>` where PieceInfo is a simplified view (row, col, piece_type as string, border edges as booleans)

Keep the existing `compute_pieces` endpoint untouched for backward compatibility.

The response does NOT include full edge geometry (bezier control points) yet — those will be populated in Phase 3 when connectors are generated. The response proves the grid engine works and returns the structural data.

For default seed handling: if `config.seed` is empty, generate a random seed string. Since we can't use OS entropy in WASM (no getrandom), use a fixed default seed like "default" for now. Phase 4 will pass a JS-generated random seed from the browser. Document this limitation in a code comment.
